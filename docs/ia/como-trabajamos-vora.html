Desde cero

Las tres ideas, antes que cualquier herramienta

Todo lo que sigue sale de un solo principio: a la IA hay que darle algo que le diga "sí, está bien" o "no, está mal". Si no tiene eso, deja de trabajar cuando el código parece terminado, y la única que controla sos vos.

"Dale a Claude un control que pueda correr: tests, un build, una captura para comparar."Guía oficial de buenas prácticas de Claude Code (Anthropic)

1. La spec (SDD)

Primero se escribe qué tiene que pasar y recién después se programa. Es como el plano antes de construir: el código se juzga contra el plano, no contra lo que a la IA le pareció.

Ejemplo: "SI el nombre de la comida está vacío, ENTONCES la app DEBE no guardar y mostrar el error debajo del campo." Esa frase es la spec. Se escribe así (con SI, CUANDO, MIENTRAS) para que no haya dos formas de entenderla. Ese formato se llama EARS.

2. El test (TDD)

Un test es un programa chiquito que comprueba otro. En TDD se escribe primero el test, se ve que falla (rojo), se programa hasta que pasa (verde) y se ordena el código.

Ejemplo: el test arma una comida con nombre "  " y verifica que la validación diga "vacío". Antes de programar falla. Cuando falla y después pasa, quedó probado que el código hace lo que dice la spec.

3. Quien hace no se califica

El agente que escribió el código no es buen juez de su código. Tiende a darle la razón a su propio razonamiento. Por eso revisa otro agente, en una sesión limpia, que solo ve el resultado y la spec.

Ejemplo: terminás de programar y le pedís al subagente revisor-requisitos que chequee cada criterio de la spec contra el código. No vio tu charla, así que no "sabe" lo que quisiste hacer: ve lo que hiciste.

Por qué el rojo es lo más importante

  1. Rojo: ver fallar el test prueba que el test sirve. Un test que nunca falló puede estar mal escrito y pasar siempre (por eso la metodología pide el "control negativo").
  2. Verde: se programa lo mínimo para que pase, sin tocar el test.
  3. Ordenar: se mejora el código (nombres, repetición) y los tests siguen en verde. Si se rompen, el ordenamiento rompió algo.

En TDD el control negativo viene incluido: si viste el test en rojo antes del código, ya sabés que detecta el caso malo.

La spec queda viva. No se escribe una vez y se olvida: cuando cambia algo, primero se cambia la spec y después el código. Así cualquiera de las cinco (o su IA) puede abrir el archivo y saber cómo tiene que funcionar.

La decisión de cada tarea

No todo lleva spec y tests: cuatro caminos según el cambio

El error más común con SDD es usar el proceso completo para todo. Un análisis de Martin Fowler cuenta que una herramienta de specs convirtió un bug chico en 4 historias de usuario con 16 criterios: "como usar una maza para partir una nuez". Elegí el camino por el tamaño del cambio.

¿Lo podés decir en una oración y toca uno o dos archivos?Un texto, un color fuera del tema, un margen, un nombre mal escrito.

A · Chico

¿Algo que andaba, ya no anda?Un error, un crash, un dato que no se actualiza, una pantalla que se ve distinta al Figma después de un cambio.

D · Bug

¿Trae, guarda, valida o calcula datos?Retrofit, Room, el repositorio, el ViewModel, las validaciones, los estados de carga y error.

C · Datos

¿Es algo que se ve?Una pantalla nueva, un componente, la navegación entre pantallas.

B · Pantalla

Hay tareas que tienen las dos cosas. Workout / 03 (detalle de un entrenamiento) es C para traer y guardar el detalle y B para dibujar la pantalla. Se hacen en ese orden y conviene en dos pull requests.

A · Cambio chico

Directo, sin spec y sin plan.

  • Se pide en una línea
  • El control automático corre igual
  • Pull request chico, se revisa en 5 minutos

B · Pantalla

La spec es la fila de PANTALLAS.md y el test es el Figma.

  • Plan, aprobás, implementa
  • Captura en dos tamaños de emulador
  • Revisor visual: APROBADA o CON CAMBIOS

C · Funcionalidad con datos

El ciclo completo: spec, auditoría, tests en rojo y después el código.

  • Spec en EARS por entrevista
  • Tests y código en sesiones distintas
  • Revisores en limpio antes del pull request

D · Bug

Primero se reproduce, después se arregla.

  • Test que falla mostrando el bug
  • Se commitea solo, y el test no se toca más
  • Arreglo hasta verde, y la spec suma el caso

    La IA te entrevista y escribe la spec

    Sesión 1 · Sofi + IA · en la carpeta del repo

    No escribís la spec de cero: le pedís a la IA que te haga preguntas, una por vez, sobre los casos que no están claros. Vos contestás y ella escribe.

No preguntes lo obvio.

    ValidarComida.kt
    fun validarComida(f: FormularioComida): Map<Campo, ErrorCampo> = buildMap {
    if (f.nombre.isBlank()) put(Campo.NOMBRE, ErrorCampo.VACIO)
    mapOf(
        Campo.CALORIAS to f.calorias, Campo.PROTEINAS to f.proteinas,
        Campo.CARBOHIDRATOS to f.carbohidratos, Campo.GRASAS to f.grasas,
    ).forEach { (campo, texto) ->
        val numero = texto.replace(',', '.').toDoubleOrNull()
        if (numero == null || numero < 0) put(campo, ErrorCampo.NUMERO_INVALIDO)
    }
}

    Control negativo del test que pasó a la primera: le pedís a la IA que cambie numero < 0 por numero <= 0, corra los tests, te muestre que "el cero sí es válido" ahora falla, y deshaga el cambio. Así ese test también quedó probado. Si es lógica de Room (el DAO), sus tests van en androidTest y se corren con el emulador abierto: ./gradlew connectedDebugAndroidTest.

  5. 5

    Revisores en limpio, en paralelo

    Subagentes · ninguno vio la charla
    Pedido para copiar
    Usá en paralelo los subagentes revisor-requisitos (contra specs/funcionales/registro-comidas.md)
y revisor-arquitectura sobre este cambio, y corré /code-review.
Corregí solo lo marcado como BLOQUEA, CRÍTICA o ALTA. El resto anotalo como sugerencia.

    Máximo dos vueltas de revisar y corregir. Si a la segunda sigue mal, la sesión está llena de intentos fallidos: /clear y un pedido nuevo que incluya lo aprendido. Lo dice la guía de Anthropic y lo dice nuestra metodología.

    Un revisor al que le pedís problemas casi siempre encuentra alguno, aunque esté bien. Si corregís todo, el código se llena de capas que nadie pidió. Solo lo que rompe un requisito es obligatorio.

  6. 6

    Probás vos en el emulador

    Los tests prueban la lógica; vos probás lo que ve la persona. Escribís un nombre vacío, tocás Guardar y mirás que aparezca el error debajo del campo. Captura a docs/evidencia/.

  7. 7

    Commit, pull request y bitácora

    La IA redacta; vos leés y commiteás desde tu usuario. Pull request con la plantilla, la tarea pasa a En test, una compañera revisa, aprueba y une a main. Ahí pasa a Hecha.

    * Merge pull request #12 from feature/nutrition-validar-comida (lo une quien aprobó) |\ | * feat(nutrition): validar la comida antes de guardarla | * test(nutrition): cubrir validaciones de la carga manual (rojo) | * docs(specs): agregar spec de registro de comidas |/ * ...main

    Así el profe ve en la historia el camino completo: spec, test que fallaba, código que lo hizo pasar. Es justo la "data de cómo llegaron al resultado" que pidió.

1. El control automático no deja terminar a la sesión que escribe tests en rojo

El hook del final de cada turno corre los tests y, si fallan, no deja terminar. Pero en TDD la sesión de tests tiene que dejarlos fallando. Se queda en un loop. Arreglo: esa sesión se abre con TDD_ROJO=1 claude (en Windows, PowerShell: $env:TDD_ROJO=1; claude). Si usan la app de escritorio en vez de la terminal, se crea un archivo vacío .tdd-rojo en la raíz del repo mientras dura esa sesión (va en .gitignore) y se borra al terminar. scripts/control-rapido.sh suma al principio:

# En la sesión de tests en rojo solo se controlan las reglas, no los tests
if [ "$TDD_ROJO" = "1" ] || [ -f .tdd-rojo ]; then
  ./scripts/reglas.sh || exit 2
  exit 0
fi

Por qué: el hook de Stop bloquea el final del turno mientras el script devuelva 2 (documentación de hooks de Claude Code).

2. Los tests de Room no corren donde decía

Los tests del DAO con base en memoria necesitan Android: van en androidTest y se corren con el emulador (./gradlew connectedDebugAndroidTest), a mano antes del pull request. El control automático y la CI corren test/, sin emulador. Por eso la lógica (validaciones, repositorio, ViewModel) se prueba en test/ con repositorios falsos, y en androidTest queda solo lo que es de Room.

Por qué: la documentación de Android recomienda probar Room en un dispositivo con inMemoryDatabaseBuilder y desaconseja Robolectric para esto; para probar lógica que no es la base, recomienda no levantar la base.

Faltaba

3. Un camino para cada tamaño de cambio

El ciclo de 8 pasos (capa 6) parecía para todo. Ahora hay cuatro carriles: el completo es solo para lógica de datos.

Por qué: Fowler documenta el costo de usar el proceso entero para un bug chico; la guía de Anthropic dice que planificar agrega trabajo y conviene saltearlo cuando el cambio entra en una oración.

4. Un flujo para los bugs

No estaba. Ahora: test que reproduce, commit del rojo solo, prohibido tocar el test, causa en una oración, suite completa, y la spec suma el caso.

Por qué: la guía de Anthropic pide "escribí un test que falle reproduciendo el problema y después arreglalo"; el error documentado de los agentes es debilitar el test para que pase.

Faltaba

5. Firmas vacías para que el rojo sea el correcto

En Kotlin, un test que llama a algo que no existe no compila, y eso no es un rojo válido. La sesión de tests crea las firmas vacías y el test falla por el resultado. Además, el test rojo va en un commit propio: con merge commit queda en la historia.

Para no sobrecargar

6. ktlint y Roborazzi, después

El control automático arranca solo con tests y reglas. ktlint (formato) y Roborazzi (tests de capturas) se suman si alguien tiene tiempo después del hito. Si el plugin no está instalado y el script lo llama, el control falla siempre y nadie puede trabajar.

Para no sobrecargar
